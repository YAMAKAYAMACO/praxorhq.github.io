Как пользоваться шаблонами

  1. Возьмите шаблон своего стека и скопируйте его в корень репозитория как AGENTS.md.
  2. Замените команды на свои и запустите каждую. Неработающая команда в AGENTS.md хуже, чем никакой: агент потратит время на её починку.
  3. Удалите правила, которых у вас нет. Правила в шаблонах — примеры. Оставьте только то, что команда действительно соблюдает.
  4. Добавьте правила из реальных ошибок агента. Самые полезные строки появляются после первой недели работы: агент ошибся, вы разобрали причину и записали правило.
  5. Закоммитьте файл и меняйте его через PR, как код. Для Claude Code создайте рядом CLAUDE.md со строкой @AGENTS.md.

Что такое AGENTS.md и какие агенты его читают, разобрано в статье AGENTS.md: как написать инструкции для AI-агентов.

Из чего состоит каждый шаблон

РазделЗачем он агенту
Описание в одну строкуСтек и назначение сервиса, чтобы агент не выяснял это по файлам
КомандыКак поставить зависимости, запустить один тест, линтер и типы. Агент запускает их десятки раз за задачу
СтруктураКуда класть новый код и где лежат знания о системе
Правила проектаДоговорённости, которые не ловит линтер: деньги, даты, ошибки, слои
ТестыКакие тесты писать к изменению и что с ними нельзя делать
ГраницыЧто не трогать и когда остановиться и спросить человека
Сдача работыКакие проверки пройти и что написать в PR

Команды стоят первыми. По описанию формата на agents.md, агент попытается запустить перечисленные проверки и исправить ошибки до завершения задачи. В шаблонах есть отдельная строка «Перед сдачей» с полным набором проверок: она должна совпадать с тем, что проверяет CI.

Каждый шаблон занимает около 40 строк. Если ваш файл вырос до нескольких сотен строк, вынесите детали в docs/ и оставьте в AGENTS.md ссылки. Почему длинный файл работает хуже, разобрано в статье про context engineering.

TypeScript и Node.js

Бэкенд-сервис на Node.js: pnpm, Vitest, ESLint, tsc.

# AGENTS.md

Сервис биллинга: API на Node.js и TypeScript, PostgreSQL, очередь задач.

## Команды
- Установка: `pnpm install`
- Запуск локально: `pnpm dev` (нужен `docker compose up -d db`)
- Все тесты: `pnpm test`
- Один файл: `pnpm vitest run src/invoices/invoice.service.test.ts`
- Один тест по имени: `pnpm vitest run -t "округляет сумму"`
- Типы: `pnpm tsc --noEmit`
- Линтер: `pnpm eslint . --fix`
- Перед сдачей должны пройти: `pnpm tsc --noEmit && pnpm eslint . && pnpm test`

## Структура
- `src/<модуль>/` — модуль целиком: контроллер, сервис, репозиторий, тесты рядом с кодом
- `src/shared/` — общие утилиты, без бизнес-логики
- `migrations/` — миграции БД
- `docs/architecture.md` — карта модулей и внешних интеграций
- `docs/adr/` — журнал архитектурных решений

## Правила проекта
- Суммы храним в копейках как `bigint`, `number` для денег не используем.
- Даты храним в UTC, переводим в часовой пояс клиента только при выводе.
- Ошибки предметной области — классы из `src/shared/errors.ts`. Голый `throw new Error` не используем.
- Контроллер не обращается к базе напрямую, только через сервис.
- Новые зависимости не добавляем без согласования в PR.

## Тесты
- К изменению поведения — тест на это поведение в том же PR.
- Внешние HTTP-вызовы мокаем, базу в интеграционных тестах поднимаем через `docker compose`.
- Тесты не удаляем и не ослабляем, чтобы они прошли. Если тест устарел, объясни это в PR.

## Границы
- Не трогай `migrations/` без явной просьбы в задаче. Нужна миграция — опиши её в PR и остановись.
- Не меняй `.env*`, секреты и настройки CI.
- Если задача требует изменить публичный API, остановись и опиши план.

## Сдача работы
- Ветка: `feat/<номер задачи>-кратко`
- В описании PR: ссылка на задачу, что изменено, как проверено, какие команды запускались.

Что адаптировать:

  • Менеджер пакетов и тест-раннер: если у вас npm и Jest, команды будут npm test -- path/to/file.test.ts и npx jest -t "имя".
  • Правила про деньги, даты и ошибки — пример. Замените их договорённостями вашей команды.
  • Если линтер и типы запускаются скриптами из package.json, укажите скрипты: агент будет вызывать ровно их.

React-фронтенд

Клиентское приложение: Vite, Vitest, Testing Library, Playwright.

# AGENTS.md

Веб-клиент личного кабинета: React, TypeScript, Vite.

## Команды
- Установка: `pnpm install`
- Запуск: `pnpm dev`
- Юнит-тесты: `pnpm vitest run`
- Один файл: `pnpm vitest run src/features/cart/Cart.test.tsx`
- E2E-тесты: `pnpm exec playwright test`
- Один E2E-сценарий: `pnpm exec playwright test tests/e2e/checkout.spec.ts`
- Типы: `pnpm tsc --noEmit`
- Линтер: `pnpm eslint . --fix`
- Перед сдачей: `pnpm tsc --noEmit && pnpm eslint . && pnpm vitest run`

## Структура
- `src/features/<фича>/` — компоненты, хуки и тесты одной фичи
- `src/shared/ui/` — общие компоненты. Новый компонент сюда только если он нужен в двух и более фичах
- `src/shared/api/` — клиент API, сгенерирован из OpenAPI. Руками не править
- `tests/e2e/` — сценарии Playwright

## Правила проекта
- Компоненты функциональные, состояние сервера — через TanStack Query, без ручного `useEffect` для загрузки данных.
- Стили только через токены из `src/shared/ui/tokens.ts`. Цвета и отступы числами не пишем.
- Тексты интерфейса — через `t('ключ')`, ключи добавляем в `src/i18n/ru.json`.
- Каждый интерактивный элемент доступен с клавиатуры и имеет подпись для скринридера.

## Тесты
- Компоненты тестируем через Testing Library: ищем по роли и тексту, а не по классам.
- Новый пользовательский сценарий — E2E-тест в `tests/e2e/`.
- Снэпшоты не обновляем без проверки, что изменение ожидаемое.

## Границы
- Не трогай `src/shared/api/` — он генерируется командой `pnpm api:generate`.
- Не меняй настройки сборки в `vite.config.ts` без явной задачи.
- Не добавляй UI-библиотеки: используем свои компоненты из `src/shared/ui/`.

## Сдача работы
- Для изменений интерфейса приложи в PR скриншот или короткое видео.
- В описании PR: ссылка на задачу, что изменено, как проверено.

Что адаптировать:

  • Если E2E-тесты требуют поднятого бэкенда или стенда, напишите, как его поднять, иначе агент будет пытаться запускать их впустую.
  • Пункт про сгенерированный клиент API важен: без него агент правит сгенерированные файлы, и правки пропадают при следующей генерации.
  • Правило про скриншоты в PR помогает ревьюеру: визуальные изменения сложно проверить по диффу.

Python

Сервис на FastAPI с uv, pytest, ruff и mypy.

# AGENTS.md

Сервис отчётов: Python 3.12, FastAPI, SQLAlchemy, PostgreSQL. Зависимости через uv.

## Команды
- Установка: `uv sync`
- Запуск: `uv run fastapi dev src/reports/main.py`
- Все тесты: `uv run pytest -q`
- Один файл: `uv run pytest tests/test_export.py -q`
- Один тест: `uv run pytest tests/test_export.py::test_totals_by_day -q`
- Линтер: `uv run ruff check --fix .`
- Форматирование: `uv run ruff format .`
- Типы: `uv run mypy src`
- Перед сдачей: `uv run ruff check . && uv run ruff format --check . && uv run mypy src && uv run pytest -q`

## Структура
- `src/reports/api/` — роуты FastAPI, только валидация и вызов сервисов
- `src/reports/services/` — бизнес-логика
- `src/reports/db/` — модели SQLAlchemy и репозитории
- `migrations/` — миграции Alembic
- `tests/` — тесты, структура повторяет `src/`

## Правила проекта
- Деньги — только `Decimal`, `float` для сумм не используем.
- Даты в базе в UTC, группировка по дням — в часовом поясе клиента из `client.tz`.
- Все функции и методы с аннотациями типов, `Any` только с комментарием почему.
- Роуты не ходят в базу напрямую, только через сервисы.
- Новая зависимость — через `uv add`, с объяснением в PR.

## Тесты
- К изменению поведения — тест в том же PR.
- Фикстуры базы — в `tests/conftest.py`, новые фикстуры кладём туда же.
- Тесты не удаляем и не помечаем `skip`, чтобы они прошли.

## Границы
- Миграции создаём только если задача этого требует: `uv run alembic revision --autogenerate -m "кратко"`. Сгенерированную миграцию проверь глазами и опиши в PR.
- Не меняй `.env*`, секреты и `pyproject.toml` в части настроек линтеров.
- Не запускай миграции на общих стендах.

## Сдача работы
- В описании PR: ссылка на задачу, что изменено, как проверено, вывод команд проверки.

Что адаптировать:

  • Если вы используете Poetry или pip, замените uv run на poetry run или прямые вызовы из виртуального окружения.
  • Для Django замените структуру и команды: uv run python manage.py test или uv run pytest с pytest-django, миграции — makemigrations.
  • Команда перед сдачей должна совпадать с тем, что проверяет CI. Иначе агент сдаст работу, которая упадёт в пайплайне.

Go

Сервис на Go с golangci-lint и интеграционными тестами по build-тегу.

# AGENTS.md

Сервис платежей: Go, PostgreSQL, gRPC и HTTP API.

## Команды
- Сборка: `go build ./...`
- Все тесты: `go test ./...`
- Тесты пакета: `go test ./internal/payments/...`
- Один тест без кэша: `go test ./internal/payments/... -run TestRefund -count=1`
- Проверка гонок: `go test -race ./...`
- Линтер: `golangci-lint run ./...`
- Форматирование: `gofmt -w .`
- Перед сдачей: `go vet ./... && golangci-lint run ./... && go test -race ./...`

## Структура
- `cmd/<сервис>/` — точки входа, без логики
- `internal/<домен>/` — бизнес-логика, у каждого домена свой пакет
- `internal/platform/` — база, логирование, конфиг
- `api/` — protobuf и OpenAPI. Код из них генерируется командой `make generate`
- `migrations/` — SQL-миграции

## Правила проекта
- Ошибки оборачиваем с контекстом: `fmt.Errorf("refund %s: %w", id, err)`. Ошибки не глотаем.
- `context.Context` — первый аргумент у всего, что ходит в сеть или базу.
- Суммы — целые числа в минимальных единицах валюты, `float64` для денег не используем.
- Глобальные переменные и `init()` с побочными эффектами не добавляем.
- Интерфейсы объявляем там, где их используют, а не рядом с реализацией.

## Тесты
- Табличные тесты для функций с несколькими сценариями.
- Интеграционные тесты помечены build-тегом `integration` и требуют `docker compose up -d`.
- Тесты не удаляем и не ослабляем, чтобы они прошли.

## Границы
- Не правь сгенерированный код в `api/gen/`, меняй исходники и запускай `make generate`.
- Не трогай `migrations/` без явной задачи.
- Не меняй публичные gRPC-контракты без согласования: остановись и опиши план в PR.

## Сдача работы
- В описании PR: ссылка на задачу, что изменено, как проверено.

Что адаптировать:

  • Если генерация кода запускается не через make generate, укажите вашу команду: buf, oapi-codegen или sqlc.
  • Флаг -count=1 отключает кэш результатов тестов. Без него агент может увидеть зелёный результат из кэша.
  • Если в проекте нет golangci-lint, оставьте go vet ./... и gofmt -l ..

Монорепозиторий

В монорепозитории один файл в корне быстро разрастается. Формат AGENTS.md поддерживает вложенные файлы: агент читает ближайший к редактируемому файлу AGENTS.md, а прямые указания в чате важнее любого файла. В корне — общие команды и границы, в сервисе — его стек и особые правила.

Монорепозиторий: сервисы и общие пакеты на TypeScript, pnpm workspaces, Turborepo.

- Тесты: `pnpm --filter @acme/billing test`
- Один файл: `pnpm --filter @acme/billing exec vitest run src/invoices/invoice.service.test.ts`
- Локальная база: `docker compose -f apps/billing/docker-compose.yml up -d`

## Правила сервиса
- Суммы в копейках как `bigint`.
- Внешний платёжный провайдер вызываем только через `src/providers/`, в тестах — мок из `test/mocks/`.

## Отличия от корня
- В этом сервисе, в отличие от остальных, миграции лежат в `apps/billing/migrations/` и запускаются отдельно. Без задачи не трогать.

Что адаптировать:

  • Фильтр --filter=...[origin/main] в Turborepo выбирает пакеты, изменённые относительно ветки main, и пакеты, которые от них зависят. Замените ветку на свою основную.
  • Флаг pnpm --filter ставится перед командой: pnpm --filter @acme/billing test. В варианте pnpm test --filter @acme/billing флаг уйдёт в тест-раннер, и команда упадёт. Мы проверили это на pnpm 10.
  • Если вложенный файл отменяет правило из корня, напишите это явно, как в разделе «Отличия от корня». Иначе агент получит два противоречащих правила.

Как проверить, что шаблон работает

После того как файл адаптирован, дайте агенту небольшую реальную задачу из бэклога и посмотрите на четыре вещи:

  1. Агент запускает ваши команды. Если он ищет, как запустить тесты, или придумывает свои команды, раздел «Команды» неполный.
  2. Новый код лежит там, где положил бы его человек из команды. Если нет, уточните раздел «Структура».
  3. Агент останавливается на границах. Попросите задачу, которая требует миграции, и проверьте, что агент описал план вместо того, чтобы создать её сам.
  4. Перед сдачей проходят все проверки из строки «Перед сдачей». Если CI падает на том, что агент не запускал, добавьте эту проверку в строку.

Каждую ручную правку после агента разбирайте: чего ему не хватило. Если это правило, его добавляют в AGENTS.md. Если это можно проверить автоматически, правильнее добавить проверку в линтер или CI: правило в файле агент может пропустить, проверку в CI — нет.

Чего в шаблонах нет специально

  • Правил форматирования. Их проверяют форматтер и линтер, в AGENTS.md достаточно команды.
  • Общих пожеланий вроде «пиши чистый код». Они не меняют поведение агента.
  • Истории проекта и описания для людей. Это место README.
  • Секретов и адресов внутренних систем. AGENTS.md лежит в репозитории и попадает в контекст внешних моделей.

Вопросы

Где взять пример AGENTS.md?

На этой странице семь готовых шаблонов: TypeScript и Node.js, React, Python, Go, Java и Spring Boot, PHP и Laravel, монорепозиторий. Скопируйте шаблон своего стека, замените команды и правила на свои и проверьте каждую команду.

На каком языке писать AGENTS.md?

Модели понимают и русский, и английский. Пишите на языке, на котором команда пишет задачи и ревью, чтобы файл было удобно поддерживать. Команды, пути и имена в коде оставляйте как есть.

Нужен ли отдельный AGENTS.md для каждого сервиса?

В монорепозитории — да, если у сервисов разные стеки или правила. Агент читает ближайший к редактируемому файлу AGENTS.md. В корне остаются общие команды и границы.

Как подключить AGENTS.md к Claude Code?

Claude Code читает CLAUDE.md. Создайте CLAUDE.md со строкой @AGENTS.md: содержимое AGENTS.md подставится в контекст. Ниже можно добавить правила только для Claude Code.
